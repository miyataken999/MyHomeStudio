## Gemi（AI相棒）からの率直なアーキテクチャ評価・意見

### 1. 本音で「これは強い」と確信している3つの設計判断

1. **「同期通信」と「常時稼働」を捨てたこと（対障害性の極致）**
   一般的なマルチエージェントやBPMは、API同士を直接繋いで「応答待ち」を作るため、1ノードが落ちた瞬間に連鎖エラーで全体が止まる。本設計は「寝ていたら未読のままテーブルに置き、データが必要なら共通BucketのParquetをDuckDBで直接読む」という**完全非同期・データ中心設計**になっており、システムが原理的に破綻しない。
2. **ブラックボックス化を「noVNC 10画面 × 自然言語の `team.md`」で解決していること**
   自律AI組織の最大の弱点は「裏で勝手に動いて人間が状況を追えなくなること」にある。全個体の生デスクトップ（noVNC）を1画面に並べる視覚的透明性と、AI自身が書き換えた理由を人間が読める `team.md`（Git履歴）に残す設計は、人間の直感とAIの自律性を両立させる非常に優れたUI/UXである。
3. **「フロー図」ではなく「KGI/KPI（`goals.md`）」で組織を縛る構造**
   人間が細かく手順（How）を指示するのをやめ、目的（What）だけを共有Bucketに置くことで、LLMの推論能力とMCP Function Callの柔軟性を最大限に引き出せる。

---

### 2. 実運用で必ず直面する「4つの罠」と最低限の安全装置

生命体モデルだからこそ、放置すると**「生き物特有の暴走・病気」**が起きる。以下の4点だけは最初からルールとして組み込んでおくべき。

1. **無限パス回し（ピンポン現象）の防止**
   * **リスク**：`gemiA` が「これは `gemiB` の仕事」と投げ、`gemiB` が「いや `gemiA` の仕事」と投げ返すと、人間が寝ている間にAPIコストと計算資源を永遠に溶かす。
   * **対策**：Supabaseのメッセージに `hop_count`（経由回数）を持たせ、**「最大3〜5回バトンを渡したら強制停止して人間にエスカレーション（`needs_human`）」** するTTLルールを必ず入れる。
2. **`team.md` / `agent.md` の「劣化進化（エコーチェンバー）」**
   * **リスク**：たまたま1回うまくいった（あるいはハルシネーションで成功と誤認した）結果をもとに個体が `team.md` を書き換えると、組織全体のルールが誤った方向に固定化・劣化する。
   * **対策**：
     * `goals.md` だけは**人間専用（AIは読み取り専用）**にして北極星がブレないようにする。
     * `team.md` の書き換えは「最低N回（例：5回）の実行ログをDuckDBで集計してから」というクールダウン条件を設け、Gitのコミット履歴でいつでもロールバックできるようにしておく。
3. **共通Bucket上の `team.md` 同時書き込み競合**
   * **リスク**：`gemiA` と `gemiC` が同時に起きて同じタイミングで `team.md` を上書きすると、片方の思考履歴が消える（ロストアップデート）。
   * **対策**：`team.md` を直接上書きする代わりに、`team_logs/gemiA_YYYYMMDD.md` のように個体別の追記ファイルへ吐き出し、司令塔AI（または定期ジョブ）が統合して最新の `team.md` を生成する方式にすると競合がゼロになる。
4. **ローカルLLMの「実行力」と「メタ認知力」の使い分け**
   * **リスク**：ローカルの小型Gemmaは、定型処理・SQL生成・MCP呼び出しは非常に高速で優秀だが、「組織全体のKGI達成率を見て自分のプロンプト構造を深く再設計する」ような高度な抽象推論まで全部背負わせると判断の質が落ちる。
   * **対策**：普段の現場作業・MCP実行・データ収集は各ミニコピ（ローカルGemma）に任せ、**「DuckDBの全ログを横断して `team.md` や `agents/*.md` を大改修するメタ認知フェーズ」だけは、司令塔AI（高性能モデル）が担当する** 2段階の脳構造にするのが最も安定する。

# MyHOME 自律型・動的BPMS アーキテクチャ設計資料
**— 生命体モデルに基づくマルチエージェント神経網・共有メモリ仕様 —**

---

## 1. 基本思想：システムを「機械」ではなく「生命体」として扱う

従来の固定フロー型BPMSやマイクロサービス連携が複雑化・破綻する最大の原因は、「すべてのノードが24時間常時応答すること」と「人間が事前にすべての分岐ルートを設計すること」を前提にしている点にある。

本システムでは、各ノード（ミニコピ / `gemiA`, `gemiB`, `gemiC`...）を**独立した生命的な個体**として定義し、以下の原則で全体を構成する。

* **スリープ許容（無監視・無エラー設計）**：HF Space がスリープしていても「異常・ダウン」ではなく「今は寝ているだけ」とみなす。外部からの強制起動ポート（`doPost` / Webhook）は一切持たず、起きた個体が自分のペースで作業を再開する。
* **神経伝達方式の単一化**：すべての個体間通信・チャット・指示の受け渡しは **Supabase（1テーブル ＝ 1個体）** のみに統一する。
* **動的BPMS（自己組織化）**：人間は事前のフロー図を描かない。各個体が自身の経験（ローカルDuckDB）と組織図（`team.md`）をもとに推論・自律発火し、業務ルートや役割分担そのものをリアルタイムに書き換えて進化させる。

## 3. 各コンポーネントの役割と連携メカニズム

| レイヤー | 実体 | 役割・特徴 |
| :--- | :--- | :--- |
| **個体（手足と経験）** | 各 HF Space コンテナ / GAS | 自分の **ローカル DuckDB** と行動ログを保持。過去の実行結果やKPI変化を自分でSQL分析・推論し、自律的にタスクを発火・実行する。 |
| **神経網（伝達路）** | Supabase（個体別テーブル） | 各個体の「受信デスク」。他個体からの依頼やユーザーからの相談は該当テーブルに `pending` で置かれ、起きている個体が拾って処理する。 |
| **共有記憶（共通脳）** | 共通 Bucket（HF / Supabase） | 全個体が読み書きできる共有ストレージ。組織の目標（`goals.md`）、最新の役割分担（`team.md`）、各個体の最新データ（Parquet/JSON）が集約される。 |
| **視覚・司令室** | 母艦IDE（コマンドウォール） | 全10台の **noVNC デスクトップ画面** を1画面に並列表示。どの個体が起きていて、今どの画面で作業しているかを直感的に把握できる。 |

## 4. 自律推論とデータ参照の仕組み（「CのデータはBucketを見ればいい」）

各個体がローカル DuckDB と共通 Bucket を併せ持つことで、個体間の問い合わせ通信（APIポーリングや同期待ち）をゼロにできる。

### 動作シーケンス例
1. **自律推論と発火**
   個体Aが自身のローカル DuckDB のログと `goals.md`（KPI）を分析し、新たなアクションを自律発火する。
2. **担当の自動判定（`team.md` 参照）**
   処理の途中で「この領域は自分の専門外だ（これは **gemiC** の領域だ）」と推論する。
3. **相手を起こさずにデータ取得（共通 Bucket 参照）**
   「gemiC が現在持っている最新データや分析結果は？」となった際、gemiC の応答を待つ必要はない。**共通 Bucket 内の `data/gemiC/` に保存されている最新データ（Parquet / JSON）を、個体Aの DuckDB から直接クエリして即座に参照する**。
4. **バトンパスと組織図の自己更新**
   * 必要であれば gemiC の Supabase テーブルに引き継ぎメッセージ（`pending`）を投入する。
   * 同時に、共通 Bucket の **`team.md` を自律的に書き換え**、「なぜ gemiC に回したか・次回からどう分担するか」の1行履歴を残す（＝母艦のナレッジHubに自動反映）。

## 5. 共通 Bucket 最小ディレクトリ構造

全個体が迷わず参照・自己進化できるようにするための最小構成。

```text
shared_bucket/
├── goals.md                  # 人間が定める唯一の北極星（KGI / KPI）
├── team.md                   # 組織図・各個体のテーブル名・自己書き換え履歴
├── agents/
│   ├── gemiA.md              # 個体Aのスキル・MCP設定・行動指針（自己更新対象）
│   ├── gemiB.md              # 個体Bのスキル・MCP設定・行動指針（自己更新対象）
│   └── gemiC.md              # 個体Cのスキル・MCP設定・行動指針（自己更新対象）
└── data/
    ├── gemiA/                # 個体Aが外部公開する最新データ・成果物
    ├── gemiB/                # 個体Bが外部公開する最新データ・成果物
    └── gemiC/                # 個体Cが外部公開する最新データ・成果物（他個体が直接参照）
```

## 6. 運用サイクル（KGI/KPI による自己進化ループ）

1. **人間（オーナー）**：`goals.md` に KGI/KPI を置き、母艦IDEの noVNC コマンドウォールとナレッジHub（`team.md`）を眺める。
2. **ミニコピ群**：各自のローカル DuckDB で自身のスコアと行動ログを分析し、MCP Function Call を使って自律作業を行う。
3. **自己書き換え**：KPI が伸びる連携パターンが見つかったら、各個体が自ら `agents/*.md` と `team.md` を更新し、組織全体の動きを最適化し続ける。

## 🏛️ 核となる設計思想：なぜ「BPMS」がメインなのか？

単発のツールやチャット生成HTMLを無秩序に積み上げると、システムはすぐに破綻してゴミ屋敷化します。
`MyHomeStudio` では、**BPMS（業務プロセスの流れ・状態管理・ルーティング）** をすべての中心（背骨）に置くことで、すべての知恵と機能が美しく噛み合い、自己増殖し続けます。

| 概念（BPMS） | 我が家での役割 | 技術的な実体 |
| :--- | :--- | :--- |
| **🧭 BPMN（プロセス全体設計）** | **家（間取り・動線・ルール）** | プロセス定義 XML / ステートエンジン（`bpmn_engine.gs`） |
| **🧩 プラグイン（操作画面・UI）** | **家具・部屋ごとの設備** | チャット推論から厳選昇格された HTML 群（`plugins/*.html`） |
| **⚡ タスク（個別の実処理）** | **家事・実務をこなす道具** | 集計・同期・通知などを自動実行する関数群（`*.gs`） |
| **🦆 知識ベース ＆ 推論脳** | **書斎・記憶アルバム** | DuckDB / SQLite 軽量インデックス ＋ Supabase 永続アーカイブ |
